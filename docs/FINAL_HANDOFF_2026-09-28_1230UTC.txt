PART A. WHAT'S LIVE NOW AT VERSION 143 -- 4 NEW THINGS ON TOP OF v142
----------------------------------------------------------------------------
This publish bundled two feature commits (63d370c, 87afb0d) that were built, independently
verified, and held back earlier in the session specifically so they could go live together in
one mandatory full-page-read publish instead of two.

1. NEW -- "Anomaly leader pages" tile in Ask the terminal. You shared a screenshot of a
   competitor's ("Alex", @hughesanalytics) structured multi-table answer style for a query like
   "Which subsector in Industrials had the highest combined anomaly score?" and asked for the
   same capability here. Built as a genuinely alternate render mode (existing compact-style
   answers are completely unchanged) triggered by the phrase "leader page" in a question. Open
   Ask the terminal -> look for the new "Anomaly leader pages" details/tile (same visual style as
   the existing "Examples by theme" tiles) with 10 ready-to-run example questions spanning:
     - Singular (one named group): "Show the anomaly leader page for the Travel Services subsector."
     - Combined (rank all peers, return the winner): "Which subsector in Industrials had the
       highest combined anomaly score? Show the leader page."
     - Combined + filter (min member count, or improving-only bias)
     - Combined + added columns (extra return windows, or a liquidity/turnover column)
   Each answer renders: Title -> context bar (cutoff date | metric | parent scope) -> Leader
   summary paragraph -> one-row group-summary table -> every-member table (rank/symbol/score/1D
   return) -> Coverage checklist (proves data completeness, not decoration) -> Metric footnote.
   Reuses the SAME group-ranking data (gaMean, r1, bias, counts) the compact style already
   computes -- no second calculation engine. Two small, real additions were needed to the base
   engine to make some of the 10 examples work: scoping a ranking to one named parent sector
   ("in Energy") and a minimum-member-count filter, since the existing compact style silently
   ignores both.
   ADAPTATIONS FROM THE ORIGINAL SCREENSHOT (be aware of these when comparing to Alex's version):
     - No "Company" column -- our loaded scan has no company-name field, only tickers, so nothing
       was fabricated to fill it in.
     - "Volume" in one example maps to the scan's real 20-day turnover/liquidity percentile field
       (labeled honestly as "Liquidity (20D turnover) pctl"), not raw share volume, which the
       data doesn't have.
     - A "last 5 trading days" example became "using the 5-day return" -- there's no time-windowed
       anomaly aggregate in the data, only a per-symbol 5D return field.

2. NEW -- Backtest is up to ~47x faster. The old code re-parsed the ENTIRE raw price-history CSV
   text from scratch on every single rebalance-eligible date (260 times for a daily-rebalance
   backtest over a year) -- that was the real bottleneck, not the trade/stats simulation as
   originally assumed. Now the price history is parsed ONCE and sliced from an already-parsed,
   date-indexed structure per date instead. Verified byte-identical to the old method across every
   date in two test fixtures (396 dates total) before being switched on by default. Measured
   speedup on the real fixture: 77.6 seconds -> 1.6 seconds (47.5x). This makes the EXISTING "Run
   backtest" button faster with zero change in output -- nothing to do differently, it just runs
   quicker now, especially noticeable on daily-rebalance portfolios with lots of eligible dates.

3. NEW -- "⚡ Export weights only (fast)" button in the Backtest section, next to "Run backtest".
   This came out of your question about whether there's a cheaper path to just the weights CSV
   without a full backtest run. Answer: yes, partially -- it still has to run the same no-look-
   ahead pick-selection loop (that IS what determines the weights, can't be skipped), but it skips
   the full trade/cost/P&L/drawdown/stats simulation entirely, computing only the target weights
   via the exact same formula engine() uses (now shared, extracted into reusable helpers so the
   two paths can never drift apart). Verified byte-identical Terminal_Weights.csv output vs. the
   full "Run backtest" -> download path, across equal/rank/inverse-vol weighting and daily/weekly
   rebalance (16/16 tests). Use this when you only want the CSV for RealTest and don't need the
   terminal's own stats/trade list for that run.

4. FIXED -- "Download Terminal_Weights.csv" doing nothing when clicked (the bug you reported).
   Root cause: the button's download code only tried a raw anchor-click browser download, which
   this claude.ai Artifact's sandboxed iframe silently blocks (no error thrown, so it looked like
   nothing happened at all -- exactly what you saw). Fixed by reusing the ALREADY-WORKING pattern
   sitting right next to it in the live Portfolio Tracker's own CSV export, which tries the
   proper claude.ai "downloads" capability first and only falls back to the anchor-click trick if
   that's unavailable. The publish explicitly declared that capability for this artifact to make
   sure it's actually available (it turned out to already be declared from earlier work, so this
   was a safety confirmation, not a net-new grant).

PART D. NEW IDEAS THAT CAME UP THIS SESSION (not started, for future consideration)
----------------------------------------------------------------------------
1. Parallel headless-browser instances for further backtest speed. Came out of your "can this run
   outside the browser with multithreading" question. Short answer: a full Node/multithread port
   isn't a quick win, because every function this replay reuses (upParseCSV, qmRun, engine(), etc.)
   deliberately lives inside the page's own closure -- that's what gives the no-look-ahead
   guarantee its teeth, and porting it out would mean either duplicating that logic (the exact risk
   this codebase has avoided everywhere) or a real extraction project. A cheaper middle ground: now
   that Optimization A makes each eligible date's pick-selection independent of the others (given
   the shared pre-parsed history), you could in principle run several headless-browser instances in
   parallel (same tooling this project's own test suite already uses), each handling a different
   date range or portfolio -- real wall-clock parallelism with zero reimplementation risk, since
   it's still the actual browser code running, just several copies at once. Not built, just a
   documented option if backtest wall-clock time is ever still a pain point after this session's
   47.5x sequential speedup.
2. "Open positions" follow-through: now that the open-positions table exists (from the previous
   publish) and the leader-page render pattern exists (from this session), a similar structured
   "what's still open and why" summary could eventually be applied elsewhere in the terminal where
   useful -- no concrete plan yet, just noting the pattern is now available to reuse.
3. Given the RealTest validation runner is about to get its first real test run, it might be worth
   extending Terminal_Weights.csv's contract slightly (e.g. an optional "reason" column reusing the
   Ask engine's existing per-pick filter/rule text) if the RT cross-check reveals discrepancies that
   are hard to debug without knowing WHY a symbol was picked on a given date -- speculative, only
   worth doing if the first real RT run surfaces an actual need for it.
